# 启动性能优化（2026-10-26）

基线 main `105361814e3a74e9a8db9a019d5b70dccfdb1c3b`。

## 瓶颈与处理

地图主要以代码生成几何，而不是下载大型 GLB。CPU profile 显示：铁路预约区域反复遍历每条线路的 650 段采样；短步道绘制反复以完整 3072×3072 画布作为遮罩源。仅继续压缩脚本并不能消除这些计算。

- 铁路预约查询使用 16 m 空间格，先找附近线段，再执行原来的精确线段距离判断。`railClearance` 仍保留完整距离接口；车站旋转矩形预约保持原规则。
- 步道遮罩改为按需缓存 128×128 小块，精确保留像素；新增沥青时失效缓存，避免后续步道覆盖新车道。小块通过局部 ImageData 读取，避免首次创建小块时再次复制完整画布。
- 增加 `runtime.ts` 统一地形、城市、灯光与交互模块入口，让 Vite 一起预加载依赖，代替逐项 await import 的下载链。执行仍保持地形→城市→灯光→交互顺序；资产查看器仍按需加载，云仍在首帧后加入。

## 同环境实测

运行 `CITYMAP_CANVAS_MODULE=/path/to/@napi-rs/canvas/index.js node scripts/review/loading.mjs [project-root]`。真实场景与 Canvas 材质，两轮串行运行；证据见 `loading-review/before.jsonl` 和 `after.jsonl`。先完成测试再测量，避免测试并发干扰。

| 项目 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 地形+城市构建平均 | 8.28 s | 5.44 s |
| 其中城市阶段平均 | 7.54 s | 4.73 s |
| JS 产物文件数（含延迟工具） | 22 | 9 |
| JS 原始总量 | 903,974 B | 899,928 B |
| JS 本地 gzip 总量 | 290,150 B | 283,220 B |

CPU 构建时间减少约 34.3%。gzip 为本地压缩测量，实际传输编码由 Pages/CDN 决定。仍保留 5,708 个 Mesh、3,566,521 个 position 顶点（不是三角面数）、54 户住宅。全场景几何属性、索引、世界矩阵、基础材质参数的 SHA-256 完全一致；道路遮罩 RGBA 像素 SHA-256 也完全一致。因此此次没有删减几何细节或改动道路外观，不重复制作模型造型截图。

104 项测试通过（含多种 margin 的索引/全量轨道预约一致性回归），TypeScript/Vite 构建通过。此测量不包括浏览器网络、着色器编译或手机实测，不能将 5.44 s 当作用户设备加载保证。

## 进一步空间

如果实际设备仍慢，下一步应以浏览器 Performance 记录分段定位：下载慢可用访问更稳定的 CDN/区域托管；CPU 慢可进一步把确定性的地形、场地规划或静态几何预烘焙，权衡新增下载量；首帧 GPU 慢则需按材质合批、减少首屏阴影编译或分区域渐进显示。完整场景序列化缓存还需同步处理动画节点、材质着色器回调、拾取与布局版本，不宜直接缓存整个 world 后跳过初始化。
