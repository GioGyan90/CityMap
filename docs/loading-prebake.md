# 第二轮加载优化：住宅规划预烘焙（2026-10-26）

基线 main `18d48164f5e554ed570517a3c4920125bad195fb`。保留上一轮热修复的逐阶段启动，未合并带副作用的初始化模块。

## 实施

- `scripts/bake-residential.mjs` 在构建机运行真实城市规划，输出 14 组住宅小区、54 户的完整地块、门口、步道与庭院坐标。`npm run build` 自动先执行预烘焙，再 TypeScript、Vite 和生产启动依赖检查。
- `src/generated/residentialPlans.ts` 是可复现的生成文件，随仓库保存。客户端验证输入后直接读取数据，省去重复的多边形裁切、候选筛选与步道寻路。房屋和植物仍按原流程生成，没有减少细节。
- 校验包含当前占地、出入口预留通路、地标分区、车站预约、公路控制点与宽度、铁路规划以及真实地形 Float32 数据。输入不同则回退原规划函数；烘焙始终强制执行原算法，避免读取旧数据生成新数据。修改规划算法后应运行构建更新生成文件；开发模式下可单独 `npm run bake:residential`。
- 停车与步道预约采用 12 m 空间索引，随城市构建中新增的路径增量更新。最终判断保持原线段距离逻辑。当前生产预约列表只追加；缩短列表会清空重建索引。
- 隧道预约与覆土查询先用真实采样边界排除远处位置，再执行原精确计算；`tunnelLocation` 的完整距离查询保留。
- 地形地标平台的固定目标高度提前计算，避免每次高度查询重新枚举分区和重复求平台高度。

## 实测与取舍

同一环境使用真实场景几何和 Canvas，道路/城市串行两轮。证据：`loading2-review/before.jsonl`、`after.jsonl`；复现脚本 `scripts/review/loading.mjs`。新版报告 `planningSource=baked`。

| 项目 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 地形+城市构建平均 | 6.91 s | 5.11 s |
| 城市阶段平均 | 6.20 s | 4.59 s |
| JS 本地 gzip 总量 | 290,610 B | 303,969 B |
| 住宅 | 14 组 / 54 户 | 14 组 / 54 户 |

本轮 CPU 构建减少约 26.0%。增加约 13.4 KB gzip 规划数据，换取客户端免做重复规划，**这轮是计算优化，不是下载文件变小**。gzip 为本地测量，实际传输编码由托管决定。各轮机器负载有变化，不把不同轮基准直接相乘作为累计提速保证。

全场景的几何属性、索引、世界矩阵、基础材质参数 SHA-256 与道路遮罩 RGBA 像素 SHA-256 均与基线相同；仍为 5,708 Mesh、3,566,521 个 position 顶点。此轮没有模型造型变化，因此以生成结果一致性验证替代重复造型截图。

107 项测试通过，新增覆盖预烘焙结果与实际城市一致、占地/地形/通路变化导致校验失效、通路索引与全量查询一致及增量追加、隧道快速排除与原精确计算一致。生产构建及启动模块依赖检查通过。

计时不包含网络、WebGL 上下文、首帧着色器编译与真实手机表现。现有云浏览器 WebGL 不可用，不能宣称完整浏览器首帧或设备帧率验收。
