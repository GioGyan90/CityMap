# 第三轮加载优化：直接写入合批缓冲区

2026-10-26，基于 main `6ac31cb434bbe561ea0059ca04e65e0e19c41fd5`。保留真实跨街商业区、二层蓝序厅、屋顶穹顶及此前所有场景内容。

## 瓶颈及修改

Node CPU profile 显示，住宅细节合批与植物烘焙中，`toNonIndexed`、属性复制、矩阵变换以及 `mergeGeometries/mergeAttributes` 消耗较多CPU并制造临时数组。住宅合批在一轮profile中约0.63秒，植物烘焙约0.38秒；此单轮数据只用于定位，提速结论采用下述串行对照。

新增纯数据模块 `src/geometryBatch.ts`。先计算每个材质桶的最终顶点数量，再一次性分配 position/normal/uv/color 缓冲区；通过源索引直接按原顺序展开到最终数组，同时执行与Three.js原有流程相同的矩阵/法线变换。避免为每个小零件先复制完整几何、展开索引，再在最终合并时复制一次。

- `batchResidentialGeometry` 接入新流程，保留玻璃明暗分组、颜色、UV缺省值、顺序及原有节点结构。
- `bakePalm`（同时用于树、花盆等植物）接入同一流程，保留根节点的局部坐标、材质色与顶点色相乘、包围盒及包围球。
- 不修改源几何，复用原件与资产查看器仍能读取原始部件。
- 不减面、不删模型、不改贴图分辨率；启动模块依然分阶段加载。

## 实测

使用相同Node、真实Canvas纹理和完整实际城市。基线使用独立干净worktree；按“基线两次→新版两次”交替两轮，所有计时进程串行执行，不与测试/构建并行。复现入口为 `scripts/review/loading.mjs [worktree]`，需指定 `CITYMAP_CANVAS_MODULE`。原始记录及汇总在 `docs/loading3-review/`。

| 指标 | 基线4次平均 | 新版4次平均 |
| --- | ---: | ---: |
| 地形+城市CPU生成 | 3.946秒 | 3.333秒 |
| 城市阶段 | 3.428秒 | 2.842秒 |
| 地形阶段 | 0.518秒 | 0.490秒 |
| 可达JS chunk总量，原始 | 949,990 B | 950,365 B |
| 可达JS chunk本地gzip总量 | 307,583 B | 307,737 B |

总CPU生成时间减少约 **15.5%**；城市阶段约 **17.1%**。地形阶段未修改，其时间差属于运行波动。gzip仅增加154字节，按index入口及静态/动态依赖递归统计全部22个可达JS chunk，不包含本地dist残留旧哈希文件。实际HTTP编码由Pages决定。

这轮优化CPU处理，没有声称网络下载显著变快。计时不含浏览器WebGL上下文、着色器首编译、首帧GPU工作或手机性能；云浏览器WebGL受限，尚不能给出这些指标。

## 正确性与回归

8次生成结果完全相同：5,638 Mesh、3,564,582个position顶点、13组住宅/50户。全场景几何属性、索引、世界矩阵、基础材质参数SHA-256，以及道路遮罩RGBA像素SHA-256均保持一致，详见before/after JSONL。

新增流式合批回归：索引/非索引输入、非均匀缩放与旋转、UV缺省值、顶点色及材质色烘焙都与原Three.js展开/变换/合并流程逐浮点值一致，并检查源position缓冲区未被修改。

`npm test` 113项通过；`npm run build`（住宅预烘焙、TypeScript、Vite、生产启动依赖检查）通过；`git diff --check`通过。因为实际几何和道路像素完全相同，本轮不重复制作建筑造型截图。
